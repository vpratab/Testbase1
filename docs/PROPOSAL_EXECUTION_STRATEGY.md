# Seven-Topic Proposal Execution Strategy

## How the shared work increases competitiveness

The shared PZDR/RTVLAS foundation gives every proposal:

- a working prototype rather than only a concept diagram;
- deterministic native execution for critical paths;
- Python modeling for rapid experimentation;
- signed and tamper-evident test evidence;
- negative tests and known-boundary statements;
- one-command reproduction;
- a credible Phase I-to-Phase II implementation path.

The proposal narrative should disclose reuse as company background capability,
but the technical objectives and deliverables must remain topic-specific.

## Phase I work-package pattern

Each proposal should use the same disciplined structure:

1. Establish sponsor-specific mission requirements and acceptance metrics.
2. Ingest government-furnished or approved representative data.
3. Adapt the shared native kernel behind the topic-specific contract.
4. Run controlled baselines, ablations, stress, and adversarial tests.
5. Measure accuracy, latency, memory, scale, false alerts, and failure behavior.
6. Conduct an operator or government-SME review.
7. Deliver architecture, prototype, evidence package, transition plan, and
   Phase II design specification.

## Evidence hierarchy

Proposal claims should identify their evidence level:

1. synthetic unit test;
2. simulated mission scenario;
3. real public data with synthetic anomaly;
4. real external hardware or provider data;
5. representative sponsor environment;
6. operational sponsor environment.

This prevents a high laboratory metric from being mistaken for operational
validation and makes the transition plan more credible.
